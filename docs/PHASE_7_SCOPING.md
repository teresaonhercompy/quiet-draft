# Phase 7 — Advanced Media Tools Scoping

**Date:** 2026-08-02

**Status:** Phase 7A approved and implemented as a test candidate; Phase 7B held by user request; Phase 7C scoped only

## Accepted baseline

Phase 6 is accepted after one week of regular iPad use. Local data, local draft saving, canon import/search, and the practical iPad-to-Notes-to-Scrivener transfer path are working. Phase 7 must preserve that baseline, the public-shell/private-content boundary, offline drafting, and every production browser-storage identifier.

The three requested enhancements are technically feasible and belong in Phase 7. They do not require the optional Phase 8 intelligence layer.

## Phase 7A — Hardware Media Controls

### Goal

Allow the iPad's available system or Magic Keyboard media controls to operate the existing local music player while the user writes, including in Quiet Draft Focus Mode.

### Proposed V1 scope

- Register the existing audio player with the browser Media Session API when supported.
- Connect system **Play**, **Pause**, **Previous Track**, and **Next Track** actions to the existing player functions.
- Publish the selected track title, artist, album, and available local artwork to the system media surface.
- Keep playback opt-in: no autoplay and no restoration of playback intent.
- Keep the current visible player controls as the authoritative fallback.
- Do not intercept ordinary typing keys or add global shortcuts that conflict with writing.
- Treat physical-key behavior as capability-based rather than guaranteed; verify it on the user's actual iPad, keyboard, and iPadOS version.

### Feasibility and risk

The Media Session API defines handlers for play, pause, previous-track, and next-track actions generated by physical or onscreen system controls. Browser support remains non-universal, so implementation must feature-detect every action and fail silently to the current controls. This is a focused addition to the existing player and does not require a storage migration.

Apple identifies the selected Magic Keyboard as having a 14-key function row. Phase 7A is therefore sufficiently scoped for a small implementation and physical acceptance test on the confirmed device.

### Acceptance test

- Start local music explicitly.
- Enter Quiet Draft Focus Mode.
- Verify play/pause and track navigation from the available keyboard/system media controls.
- Verify that unsupported controls do nothing harmful.
- Verify that draft typing, autosave, Focus Mode, and background-pausing behavior remain unchanged.

### Implementation state

The Phase 7A test candidate uses a small capability-detected controller around the existing audio element. It registers each system action separately so partial browser support remains harmless, publishes local title/artist/album/artwork and position when supported, and performs no browser-storage migration. The visible player remains authoritative. No global media-key or writing-key interception was added. After the first physical pass revealed that audio could survive standalone-app dismissal, the corrected candidate suspends the Media Session and refuses background play/track actions whenever the document leaves the foreground.

## Phase 7B — Center-panel Visual Archive

**Hold:** The user explicitly deferred Phase 7B. This section remains a record of the earlier scope only and is not authorization to implement it.

### Goal

Upgrade the existing **Images** tool from a right-rail scroll target to a proper center-panel image browser while keeping the smaller right-rail preview.

### Proposed V1 scope

- Reuse the existing locally imported gallery records rather than create a second copy of every image.
- Keep the right-rail Image Preview synchronized with the center workspace.
- Show one large fitted image in the center panel.
- Add previous, next, random, swipe, and left/right arrow navigation.
- Add a thumbnail strip or compact grid for direct selection.
- Add an explicit full-screen/immersive viewer with a visible exit path.
- Support bulk multi-image import from Files.
- Show position, filename-derived title, and optional existing caption.
- Preserve the accepted bundled public scenes and private local imports.
- Work offline after import.
- Do not scan the iPad Files app, enumerate arbitrary folders, upload images, or add cloud sync.

### Storage approach

The current `gallery` object store should remain authoritative so the center viewer and right rail reference the same records. Importing an image copies it into browser-managed local storage; the original remains the backup in Photos.

For approximately 900 images, V1 should:

- require explicit selection from Photos or Files rather than attempt to scan the Photos library
- import in manageable batches rather than ask Safari to process all 900 originals in one operation
- generate lightweight thumbnails for the browser grid
- load only the selected full image and a small neighboring window into memory
- show estimated browser-storage use and graceful quota errors
- request persistent storage after a successful import

The preferred storage policy is to create device-optimized local viewing copies during import, while leaving the full originals safely in Photos. A maximum long edge around 2,048 pixels is appropriate for the 11-inch viewer and will substantially reduce storage and memory pressure. Preserving every full-resolution original in browser storage remains possible, but is not recommended until the total source-library size is known.

### Full-screen approach

Use the standard Fullscreen API when available on iPadOS, with an in-app edge-to-edge immersive mode as the graceful fallback. The app must never trap the user in full screen, and navigation controls must remain touch- and keyboard-accessible.

### Deferred unless explicitly requested

- EXIF parsing
- Facial recognition or tagging
- Automatic collections
- Cloud albums
- Image editing
- Folder watching

## Phase 7C — Dreamspeak Music Theater

### Goal

Add a new center-panel tool named **Music Theater** for two music videos, with local private playback as the primary path and optional YouTube links as an online fallback.

### Recommended source policy

1. **Primary:** import the user's confirmed H.264/AAC `.mp4` files from Files.
2. **Optional fallback:** store and open/embed the unlisted YouTube URLs only on the current device.
3. **Do not:** make the app download or extract video from YouTube.

YouTube allows creators to download their own uploaded videos through YouTube Studio, but that should remain a manual user action. The app should consume the resulting MP4 or the user's original file.

The current files total approximately 1.1 GB. Modern Home Screen web apps can often store that amount when the iPad has adequate free space, but the import would create another device-local copy and browser data remains subject to quota and storage-pressure behavior. Both files are confirmed H.264/AAC MP4s, so conversion is unnecessary.

### Proposed V1 scope

- Add one data-driven Tool Center tab for **Theater**.
- Import local MP4 files explicitly from Files.
- Store private local video records separately from the app shell and service-worker cache.
- Show a two-item library with title and a manually selected optional poster image.
- Play through a standard HTML video element with native controls.
- Support inline playback, full-screen playback, scrub, volume, and play/pause.
- Remember the selected video and approximate position, but never autoplay.
- Pause video when the app leaves the foreground.
- Provide optional locally stored YouTube URLs as online-only fallback actions.
- Make source type and availability clear: **Local · Offline** or **YouTube · Online**.
- Never commit video files, URLs, titles, or poster art unless separately approved as public.

### Privacy and offline behavior

Local MP4 playback best matches the existing architecture and works offline. Unlisted YouTube videos are not private: anyone with the URL can watch and share them. An embedded or linked YouTube player also requires a network connection and sends playback requests to YouTube. Therefore, YouTube should remain an explicit optional fallback rather than the primary library.

### Storage approach

Video should use a separate `dreamspeak-theater` IndexedDB database or an isolated video store, not the service-worker cache. This makes deletion and quota troubleshooting clearer and avoids changing accepted music/image record shapes. Because video files can be large, the two MP4 file sizes must be confirmed before implementation.

### Deferred unless explicitly requested

- Downloading videos from YouTube
- Streaming proxies
- Video editing or transcoding inside the browser
- Automatic poster-frame extraction
- Playlists beyond the small local theater
- Background video playback

## Phase 8 boundary

None of these enhancements requires AI, a backend, authentication, or cross-device sync. Phase 8 remains unapproved. If future work requests automatic tagging, visual search, manuscript-to-image matching, cloud synchronization, or AI recommendations, that work must pass the separate Phase 8 privacy and data-flow gate.
